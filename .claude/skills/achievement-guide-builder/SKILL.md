# 全成就攻略 → 导入格式 JSON

把别人写好（或用户自己写好）的全成就攻略，按它原有的章节结构拆开，让每个成就各就各位，产出一份能直接拖进「攻略编辑器 → 导入攻略」的文件。

## 需要两样输入

**成就清单 JSON** —— 决定 `achievement_id` 能填什么。这份文件里的 `apiName` 是唯一合法的取值，任何猜测都会产出关联不上 Steam 数据的条目。用户从**游戏详情页的「导出成就列表」**按钮拿到它，里面只有名称和描述。

这份文件**不含任何分类信息**，这是有意的：哪些成就归哪一类，正是你要从攻略正文里读出来的东西。所以 `categories` 和每条成就的 `type` 都得你自己定，见下面的「分类怎么定」。

产出文件的 `guideName` 也自己起一个能认出来的名字（「默认攻略」或攻略本身的标题都行）—— 一款游戏可以有好几版攻略，用户是靠这个名字在工具里对应的。

**攻略正文** —— 用户直接粘贴的文本，或者一个 `.md` / `.txt` / `.html` 文件路径，也可以是网页 URL。

两样缺一就问用户要，不要凭游戏名猜成就。只有攻略、没有清单的话，明确说明必须先导出清单。

## 动手前

读一遍 `references/guide-json-format.md`。那里有完整 schema、每个字段的渲染位置、七个内置分类，以及一份可原样导入的示例。下面只讲怎么把攻略映射进去。

## 工作流

1. **读清单**，建一张 `apiName → 名称` 的表。清单只给名称和描述，分类全靠下一步从攻略里读。顺便看一眼名称和描述是什么语言 —— **不是中文的话**，每条备注开头要多写一段，见「清单不是中文的时候」。
2. **读攻略**，认清它的组织方式。常见三种：按流程章节（「第一章 / 第二章」）、按成就类型（「剧情成就 / 收集成就 / 挑战成就」）、两者混用（章下面是类型）。**沿用攻略自己的切分**，不要另起一套。
3. **逐成就定位**，在攻略里找到它出现在哪一段。同一个成就在攻略里被反复提到的，归到第一次给出完整解法的那一节 —— 跨章节的要特别留意，见下面的「跨章节成就」。
4. **生成 JSON**，按下面的映射表往字段里填。
5. **跑校验**：`node scripts/validate-guide-json.mjs <产出.json> <成就清单.json>`。第二个参数会核对每个 `achievement_id` 是否真的命中清单，这一步不要省。
6. **写文件**并告诉用户路径。文件名建议 `<游戏名>-全成就攻略.json`。

## 字段映射

依据界面实际渲染的位置（`src/components/Guide/GuideTimeline.tsx`）：

| 攻略里的东西 | 写到哪 | 在界面上出现在 |
|---|---|---|
| 章节 / 分类标题 | `timeline[].chapter` | 章节头部大字 |
| 本章导言、要点概览 | `timeline[].description` | 标题下方常驻一行 |
| 本章完整正文（没归属到某个成就的部分） | `timeline[].content` | 章节详情弹窗 |
| 某个成就的做法 | `sub_achievements[].note` | 成就名下方常驻一行，纯文本 |
| 某个成就的长步骤、图表说明 | `sub_achievements[].content` | 成就详情弹窗 |
| 易错过成就警告 | `guide.game_notes.missable[]` | 每项 `{achievement_id, chapter, reason}` |
| 二周目 / 存档继承 | `guide.game_notes.new_game_plus` | |
| 通用技巧、难度建议 | `guide.game_notes.tips` | |

`note` 是常驻的，一句话说得清就放这里；`content` 要点击才展开，长内容才用它。两者都是纯文本和 HTML 的区别 —— `content` 用 `<p>` 或 `<br />` 分段，`note` 里不要放标签。

攻略里如果给某个章节指定了一个「代表成就」（比如章节标题就是成就名），填进 `timeline[].achievement_id`，它会在章节顶部单独显示并带图标。没有这种成就的章节就写 `""`。

## 跨章节成就

有些成就要跨好几章才做得完 —— 击杀同一个目标三次、在第二 / 六 / 八章各听一对二重奏、两章的保险箱都要搜。攻略作者会在提到的每一章里都写一遍。

**成就条目只放一处**，放在攻略**第一次给出完整解法**的那一节。同一条成就写进两个 `sub_achievements`，工具里会变成两行互相独立、各算各的条目，章节完成度也会重复统计 —— 那不是在描述同一个成就的两次机会，是两条不同的记录。

**其余章节改在章节描述里提醒。** 在那一章的 `timeline[].description` 末尾追加一行，说清这条成就归在哪、这一章要做什么：

```
本章还能再完成一次「XXX」—— 它归在第四章，本章要杀掉帕欧罗第二次。
```

同时在那条成就自己的 `note` 里按顺序列出涉及的章节（如「第四、六章各能杀一次」）。

**两边都写**，因为读的人可能从任意一头进来：翻到第六章的人会看章节描述，直接搜到那条成就的人看的是备注。

## 清单不是中文的时候

有些游戏导出的成就名和描述全是英文。工具里显示的也是原文，而攻略作者有的会顺手翻译，有的一路用英文写下来 —— 两种情况要处理，做法一样。

**每条成就的 `note` 开头先写中文名称和中文描述，空一行，再写攻略正文：**

```
中文译名
中文描述

攻略里的解法说明……
```

几条要求：

- **作者自己翻过的，用他的措辞。** 不要另译一份 —— 同一个成就在他笔下和你笔下叫两个名字，读者会以为是两条不同的成就。
- 描述从清单的 `description` 来（那是 Steam 官方文案），短的照译，不要自己概括。
- 攻略正文那段（空行之后的部分）保持原样照抄，不要顺手也翻了。
- **清单本身就是中文时不加这段**，`note` 直接写解法，不要重复工具已经显示在成就行上方的名字。

## 分类（type）怎么定

按攻略里那一节的语义往七个内置分类上靠：

剧情推进 → `main`，支线杂项 → `side`，找东西 → `collect`，打怪打 BOSS → `combat`，需要满足条件才触发 → `condition`，难度相关 → `difficulty`。够用就用内置的，**不要为每章新建分类** —— 章节已经由 `chapter` 表达了，再给每章配一个分类等于把同一件事说两遍，色板还会拉得很长。

实在靠不上内置的七个，才新建：key 用小写英文或数字连字符（如 `multiplayer`、`dlc-1`），写进 `categories.custom` 并给一个不撞色的十六进制颜色。兜底是 `misc`。

新建分类的 `color` 不要和内置七个的默认色撞。可以按色相均分挑一组，例如 `#4dabf7`、`#f783ac`、`#20c997`、`#ffa94d`。

## 硬性规则

- `format` 必须精确是 `achievement-engine-guide`，`formatVersion` 写 `1`。写错工具只会说「无法识别该文件」。
- `achievement_id` **一律用清单里的 `apiName` 原样**。写成展示名不会让导入报错，但那一行从此没有图标、统计不到解锁进度 —— 这是最难发现的一类错误。校验脚本第二个参数就是查这个的。
- 不要写 `_uid`，导入时由工具重新分配。
- 不要写 `sub_achievements[].items`，类型里还留着但工具不渲染它。
- **清单里有、攻略没提到的成就不能漏**。单开一个「其他」章节装起来，`note` 用清单里的 Steam 描述。用户导入后是靠成就总数对不对得上来判断有没有出错的。
- 攻略提到、但清单里没有的成就名：丢掉，最后单独列给用户看，可能是 DLC 成就或者识别错了。
- 跨章节的成就**只写一条** `sub_achievements`，其余章节在 `description` 里提醒 —— 写两条会变成两行互相独立、完成度重复统计的记录。
- 自建分类只要被 `type` 引用，就必须在 `categories.custom` 里有声明，否则配色静默退化成灰色。
- 外部攻略的图片带不进来（工具内的图片是内嵌 base64 的）。在原本有图的位置留一行「（此处原攻略有图：xxx）」说明即可。

## 收尾

给用户一份简短交代，包含：

- 产出文件路径，以及跑了校验、结论是通过
- 章节数与成就数
- **哪些成就是跨章节的**，分别归在了哪一章、在哪些章的描述里留了提醒 —— 用户核对时要能一眼看出这些是有意只放一次的
- **没被攻略覆盖、被归进「其他」的成就有哪些** —— 这些是用户需要自己补的
- 被丢掉的成就名（攻略里有、清单里没有的）
- 分类的构成：用了哪几个内置分类，自己新建了哪几个、为什么
- 清单不是中文的话，说明译名是照作者用的，还是自己翻的

任何一步没把握（章节结构看不清、成就名对不上、攻略不完整）就直说，不要用编造的内容把条目凑满。
